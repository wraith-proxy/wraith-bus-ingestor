# ADR 0011: Contract-first dbt

**Status:** Accepted 2026-11-15. Code complete on `feature/TJP-14114` (`dbt/build.sh` now publishes through the SLA stamp), unmerged until the owner pushes; every step of the CI workflow passed inside the runner image against that branch. Nothing here has run against the live warehouse or the live systemd units; this ADR is updated again after cutover.
**Date:** 2026-11-15
**Related:** spec #43, tickets #44-#57, [ADR-0007](0007-parquet-archive.md), [ADR-0009](0009-fast-nightly-build.md), [ADR-0010](0010-eta-from-daily-statistics-and-3-day-hot-window.md), [contracts](../contracts.md), [cutover runbook](../runbook-cutover.md), [spikes](spikes.md), `contracts/policy.py`, `contracts/validate.py`, `ops/compile_metrics.py`, `ops/sla_check.py`, `ops/ready_gate.py`, `ops/sql_ratchet.py`, `ops/cutover.sh`

## Context

Before this work nothing in dbt was generated. The dbt sources, schema yml, tests and the ontology were written by hand, and the contract followed the SQL, so they drifted (the design audit found 17 divergences; the Parquet that dbt actually reads had no contract; the intermediates had none either). A contract change could pass CI and still break a reader, a column type or the served warehouse. The nightly build ran on a 03:00 timer that could race the extract. There was no proof a move to generated output was safe, and no governed layer through which an agent could ask for a metric.

The owner's aim is a proof of three claims: `wraith-modelgen` generates the mechanical dbt layers from unmodified ODCS 3.2.0 contracts; the contracts gate their own change; and metrics defined once above the marts can be served to agents.

## Decision

1. **Contracts are the truth.** Six ODCS contracts plus a new `bus-positions-extract` contract for the Parquet that dbt reads. Hand-only settings (external location, freshness, expectations) are carried as contract custom properties and emitted by the generator.
2. **Generated sources and tests via modelgen.** `modelgen` (0.16.0, released, baked into the CI image) generates the bods sources yml, schema yml and singular tests from the contracts. The hand-written bods sources yml is deleted. `ops/dbt_sandbox.sh` patches the generated row-count test instead.
3. **Drift gate.** CI runs `modelgen check --from-contract --diff`, falling back to `python3 contracts/validate.py --generated`, which regenerates to a temp dir and diffs. A difference in the version header alone passes, so a modelgen release does not break the next branch; until modelgen ships its own ignore option the header is regenerated and committed after each release.
4. **Breaking-change gate reads compiled SQL.** `contracts/policy.py` compares a changed contract with its `origin/main` version and fails on: a breaking change without a major bump; a removal with no `sunset` or before it; a column removal while compiled SQL still reads it (named reader; `select *` resolved to named columns, sqlglot over `dbt compile` output, not Jinja source); an added column without a valid `backfill`. CI has two steps (expand/contract, compiled readers).
5. **Policy custom properties.** `sunset`, `backfill` (`derive`, `null-before`, `replay`) and `consumes` are ODCS `customProperties` arrays of `{property, value}`, because ODCS itself has only `deprecated: boolean`. History tables are never rebuilt and no contract change is applied by full refresh.
6. **Ossie metrics compiled to MetricFlow, with exclusions.** Metrics are authored in `contracts/metrics.ossie.yaml` and compiled deterministically by `ops/compile_metrics.py`. Percentile and median metrics do not compile (no p90 of p90s), and any metric over `eta_models` must filter `operatorRef != '*'` (rollup rows repeat the same pings). `validate.py` checks the Ossie model against the contracts, so a metric bound to a missing column fails. The ontology objects and links are still the Foundry-style file; the design's decision to migrate them to Ossie's ontology spec is **not** done in git.
7. **SLA data-as-of table.** `ops/sla_check.py publish` stamps a `_meta` table (`data_as_of`, `contract_version`) INTO the staged warehouse and only then swaps it over the served file, so the served file cannot disagree with its own stamp. `data_as_of` is the newest ping in the extract Parquet. A `latency` breach against the marts contract is reported but never fails the publish (it is a ticket, not a reason to go dark); a failure to stamp stops the build and leaves the previous marts serving. `dbt/build.sh` calls it in place of the bare `mv`, after the contract gate.
8. **Extract-ready marker and event-triggered build.** An extract unit lands the Parquet; `ops/ready_gate.py` validates the whole window against the extract contract and writes `dbt/data/.extract_ready` only if every error-severity check passes. A `.path` unit on the existing `wraith-bus-build.service` (memory limit, window, failure hook kept) fires on the marker, which is consumed before the build starts so a failing build cannot retrigger itself. `ops/install_event_trigger.sh` installs this and disables the 03:00 timer in the same run; it needs sudo, so the owner runs it. The Grafana alert rules were changed in git to add a `waiting on the extract` rule with `severity: waiting`; whether that routes without paging is not verified here and the provisioning is not deployed.
9. **SQL ratchet.** `ops/sql_ratchet.py` fails CI when hand-written model SQL grows past `ops/sql_baseline.txt` (code lines with comments stripped, 653; raw 1512, recorded only). The number may only go down.
10. **Scripted cutover with a rollback limit.** `ops/cutover.sh` (`--dry-run`, preflight, stage echoes, logs, backup, BASELINE and CANDIDATE built on copies of the persistent warehouse, `ops/cutover_compare.py` exact on keys, counts and non-DOUBLE columns and tolerance on DOUBLE, offline lint then validate on the owner's `go`, atomic swap keeping the old file). The candidate is a copy because the 8-day history exists only in that file. Rollback is lossless only within `EXTRACT_DAYS=4`.
11. **`dbt/build.sh` changed last, and only here.** Its one change is the publish step: the bare `mv` became the `sla_check.py publish` call above. It was held back until every other card was committed, so the build script was never edited on top of unfinished work. It cannot be run end to end off the live host; it is covered by a syntax check and a test that pins the wiring, and its first real run is the first event-triggered night.
12. **MetricFlow needs a time spine and a time dimension.** Spike (c) found `dbt parse` and `mf validate-configs` fail without (1) a time spine model and (2) an `agg_time_dimension` on every measure. The marts have no time column by design, so the spike added a day-grain spine and a constant `cast('2000-01-01' as date)` dimension to a sandbox copy only: 0 validation errors, peak 216 MiB. Consequence: that dimension makes time-based queries meaningless. Until the semantic layer is switched on, the generated `_semantic.yml` stays in `dbt/semantic/`, outside `model-paths`, and the compiler emits neither. Switching on means choosing between a real time column on the marts and the constant.

## Alternatives rejected

Downgrading the contracts to what modelgen 0.14.1 understood (proves less); `datacontract dbt sync` as the generator (corrupted an unrelated file); the ontology as the dbt generation input (least trustworthy input); `transformLogic` in contracts for the segmentation (moves hand SQL into unverified YAML); a multi-week strangler migration (replaced by one weekend cutover); free-form text-to-SQL for agents.

## Consequences

- A hand edit to a generated file, a breaking or unbackfilled contract change, a removal a reader still needs, SQL growth, or an ontology/metric that disagrees with a contract now fails CI. Because CI has not run on a push, none of these gates has gated a real merge yet.
- Deleting the hand-written yml means generated output is the only definition of those models; a modelgen release can change the header and needs a regenerate commit.
- The cutover cannot be undone losslessly after four days.
- The Ossie spec was a draft; the compiler is ours, so a spec change is ours to absorb.

## What is not yet proven

Everything that needs the live system: that the generated dbt output reproduces the hand-written results on the real warehouse (the compare gate exists, never run for real), `contract: enforced` behaviour on the real incremental models, the installed units, three event-triggered nights with zero pages, and the rollback rehearsal. The MCP server for agents (phase C) is a separate project and not started in this repo.
